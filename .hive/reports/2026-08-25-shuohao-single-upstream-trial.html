只选 shuohao-skills：上海雨夜试跑

用用户已有的 story.json、INTENT.md 和 14 镜执行表，投影成 shuohao 的 Outline / Art / Script 数据，并运行其原生校验器。没有调用模型、没有修改 H3Storyboard 数据库、没有提交 4090 任务。

最终裁决：选它，但只采用 novel-script 核心。Scene/Beat 和确定性质量门适合作为 P2 Script Studio 的唯一上游参考；Outline 需要去短剧模板化，声音和 H3 Prompt 必须继续服从 H3Storyboard 自己的协议。

10 道 Script 质量门

门禁结果对 H3 的价值
目标时长 ±15%通过避免剧本与生成预算完全脱节；H3 后续应改用逐 beat 估时与镜头实测校准。
单句对白 ≤35 字通过保护 H3 原生中文对白的可说性。
说话人属于场景角色通过可直接映射 Character ID，避免错人说话。
钩子/收束与前三拍认领通过可保留为可选内容模式，不做所有影片的全局硬门。
每场至少一个动作通过避免只能听不能拍的“广播剧”。
动作与对白分离通过正是 H3Storyboard 需要的 ScriptBeat discriminated union。
故事 beat 认领通过可改名为 story obligation，不绑定“爽点”。
角色/场景/光照/道具对账通过能编译到现有 Character、Asset、Scene reference。

为什么不能原样安装

  1. 单集/电影不兼容：其完整 Outline 强制至少一个 major 爽点，而且首次 major 不能在最后一集；一集项目逻辑上无法通过。
  2. 状态粒度不够：action beat 没有稳定 ID，也没有服装、人物位置、持物等 opening/ending state。上海雨夜最关键的服装连续性不会被原校验器发现。
  3. 时长只是粗估：所有动作默认 2.5 秒，151.3 秒仍被允许对应 176.5 秒目标。H3 应让每个 beat 有预算并用实际 Take 反校准。
  4. 声音边界冲突：上游报告和后续 skill 面向 TTS、soundscape 与 BGM；H3Storyboard 永远只允许 H3 原生声音或静音。
  5. 缺少持久版本链：JSON 文件没有 ScriptVersion 的 draft/locked/superseded 事务、diff 和生成历史隔离。

唯一采用方案

采用改造成 H3 原生能力
episode → scene → flowScriptVersion → ScriptScene → ScriptBeat；episode 对电影可为空，对短剧可启用。
action / dialogue 二选一带 UUID 的 discriminated union；对白保存 character_id、line、delivery。
确定性 checkup保留通用门；钩子/爽点变成可选 Genre Recipe，不写死协议。
角色/场景/道具对账直接绑定 H3Storyboard Character、Asset、Scene 与版本化状态。
粗时长估算每 beat 显式预算 + ShotPlan 编译后校验 + Take 实测回写评估。

第一版只做“导入/写作 draft → Scene/Beat → 10 道通用门 → 锁定 ScriptVersion → 生成草稿 ShotPlan”。不装其他仓库，不接外部音频，不直接提交 4090。

可复核产物

  • rain-night-outline.json：单集故事骨架和角色/场景引用。
  • rain-night-art.json：唯一厢房的场景锚点和光照。
  • rain-night-script.json：结构化 Scene/Beat 与 4 句原始对白。
