director 值得借，
但它属于导演政策层。

前两个参考解决“工作台长什么样”和“剧本如何拆成素材”；director 补上了何时允许生成、哪些资产才算当前版本，以及创作模式如何与平台工具解耦。

结论：H3Storyboard 仍是独立的本地运行时与事实源。把 director 的 Mode、资产版本、生成锁、起止状态和代表片段门禁编译为协议与 UI 约束；不把它的 Seedance/CLI 规则硬写进核心。

同一任务追踪并下载落盘每次 lease 只 submit 一次；poll 同一 task，下载/校验/hash/登记后才完成远程 URL 不是本地 canonical asset

一个必须先修正的语义缝隙

director 的“片段”最长 15 秒且可含 3–5 个摄影镜头；H3Storyboard M0 的 ShotPlan 同时承担单镜分镜和 H3 job 目标。Protocol 1.1 必须明确二者映射：单个 camera shot 继续是分镜事实，多镜生成需要显式 grouping，不能偷偷改变已有字段含义。

明确不进入核心

  • Seedance 2.0 Pro、720p、15 秒、3–5 镜等当前 Mode 配置。
  • LibTV、Higgsfield、即梦的命令、模型映射、认证和下载细节。
  • 把四种 Mode 写成永久 enum；候选 Mode 也不能冒充已验证能力。
  • 直接复制 style、音色或媒体资产。它们属于 skill/作品包，不属于 runtime。

实施顺序

  1. M1A：先落 Mode、资产生命周期、manifest/lock 快照、起止状态、语义 reference requirements 与代表性门禁。
  2. Protocol 1.1：用 migration 和真实 HTTP + SQLite 测试证明旧项目可升级、旧任务不可被改写。
  3. M1B：再接真实 provider worker；adapter 读取实时 capability，不能弱化上层 contract。
  4. M2：代表 take 通过后开放批量与多模态输入审计。
