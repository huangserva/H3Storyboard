Architecture decision · 2026-08-11

不是把两个仓库缝起来，
而是抽取两套正确能力。

H3 Storyboard 的产品核心，是把完整剧本、计划镜头、H3 多模态输入、生成任务和实测结果变成一条可追溯的本地工作流。

结论：建立独立项目。借鉴 filmstoryboard 的桌面工作台与项目工程能力，吸收 xyz-video-* 的叙事、参考素材与 QC 方法；协议、数据库、任务引擎和 H3 adapter 重新设计。

两个项目分别擅长什么

filmstoryboard

Flutter / Dart · Windows desktop · SQLite/Drift
  • 已有项目入口、故事设计、拍摄脚本、分镜画板、视频分析、生成与导出等完整桌面模块。
  • 仓库内带 H3 手册、H3 prompt adapter、本地多参考任务测试和 Windows 安装/更新链路。
  • 强项是“可见、可点、可保存”的生产工作台，以及成熟的桌面交付经验。

不照搬：大体量 Flutter 应用边界、任务层字符串判错、Windows 专用路径假设。

xyz-video-creator / skill

Python scripts · JSON artifacts · agent-first workflow
  • 明确以完整 narrative 为单一故事主线，再派生 framework、scenes 与 shots。
  • video_references 按“角色、道具、构图、阶段、目标状态”等用途组织，不把所有图片误当关键帧。
  • 包含角色参考、素材生成、自动粗筛、视觉裁定、pair-level 编辑决策与 FFmpeg 合成。

不照搬：文件夹即数据库、宿主 LLM 隐式状态、Seedance 专用执行细节和无 GUI 的操作负担。

新项目的最小闭环

  1. 创建项目并写入完整脚本版本；锁定版本。
  2. 导演台建立计划镜头，绑定用途明确的图片、视频与音频。
  3. 协议校验 H3 模式、数量上限、素材归属和幂等键后，持久化 job。
  4. Provider adapter 提交、查询、取消；任务状态与事件先写 SQLite。
  5. 每次输出形成新的 take；QC 通过后才成为“实测分镜”，旧 take 永不覆盖。
  6. 下一镜连续性只引用已批准 take 的版本化资产，形成可分支依赖图。

范围裁决

M0（当前）：协议、SQLite、本地 API、计划/实测 UI、真实 HTTP+SQLite 测试。
M1：接一个真实 H3 provider、可恢复队列、素材上传与 take 审批。
暂不做：多人云协作、时间线剪辑、自动成片、多 provider 竞速、TTS/BGM、跨镜自动修复。
